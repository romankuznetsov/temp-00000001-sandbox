# Несколько туннелей одновременно

Одна секция в `/etc/config/qwdtt` - один туннель. Все секции работают
одновременно, каждая со своим сервером, своим устройством TUN и своей таблицей
маршрутизации.

Туннель без метки забирает весь трафик, который приходит из локальной сети;
такой туннель может быть только один. Остальные берут только то, что вы
пометите правилом firewall.

## Что должно отличаться у второго туннеля

| Поле | Почему |
| --- | --- |
| имя секции | это же имя у экземпляра службы и в журнале |
| `tun_name` | два туннеля не могут создать одно устройство |
| `route_table` | каждый пишет в свою таблицу маршрут по умолчанию |
| `rule_priority` | правила с одинаковым приоритетом ненадежны |
| `fwmark` | метка выбирает, что попадет в этот туннель |
| `device_id` | сервер узнает устройство по нему; с одинаковым он считает два туннеля одним устройством и отключает их по очереди |
| хеши звонка | звонок VK - это канал до сервера, и делить его между туннелями нельзя |

Init-скрипт проверяет первые четыре и не запускает секцию, которая совпадает с
другой, - причина пишется в журнал. `device_id` и хеши он проверить не может.

## Пример: один компьютер через второй сервер

Задача: весь дом идет через `main`, а хост `192.168.1.50` - через второй
туннель.

### 1. Вторая секция

```sh
uci set qwdtt.work=qwdtt
uci set qwdtt.work.enabled='1'
uci set qwdtt.work.mode='rawtun'
uci set qwdtt.work.peer_host='IP_ВТОРОГО_СЕРВЕРА'
uci set qwdtt.work.peer_port='56003'
uci set qwdtt.work.password='ПАРОЛЬ'
uci set qwdtt.work.device_id='openwrt-work'
uci add_list qwdtt.work.hash='ХЕШ_ВТОРОГО_ЗВОНКА'
uci set qwdtt.work.tun_name='qwdtt1'
uci set qwdtt.work.route_table='51821'
uci set qwdtt.work.rule_priority='9000'
uci set qwdtt.work.fwmark='0x100/0xff00'
uci commit qwdtt
```

`rule_priority` меньше, чем у `main` (по умолчанию 10000), потому что правила
просматриваются по возрастанию приоритета: правило `main` совпадает с любым
пакетом из локальной сети, поэтому оно должно проверяться последним.

Маска в метке (`/0xff00`) оставляет остальные биты другим службам - метками
пользуются, например, mwan3 и скрипты пользователя.

### 2. Правило, которое ставит метку

```sh
uci add firewall rule
uci set firewall.@rule[-1].name='qwdtt-work'
uci set firewall.@rule[-1].src='lan'
uci set firewall.@rule[-1].dest='*'
uci set firewall.@rule[-1].src_ip='192.168.1.50'
uci set firewall.@rule[-1].family='ipv4'
uci set firewall.@rule[-1].target='MARK'
uci set firewall.@rule[-1].set_xmark='0x100/0xff00'
uci commit firewall
/etc/init.d/firewall reload
```

`set_xmark`, а не `set_mark`: он выставляет все биты маски сразу, поэтому метка
совпадет с правилом маршрутизации независимо от того, что стояло в этих битах
раньше.

**`dest='*'` обязателен.** От `src` и `dest` зависит, в какую цепочку firewall4
поставит правило, а выбор таблицы маршрутизации происходит сразу после
`mangle prerouting`:

| правило | цепочка | годится |
| --- | --- | --- |
| `src` зона, `dest` `*` | `mangle_prerouting` | **да** |
| `src` зона, `dest` зона | `mangle_forward` | нет, уже после выбора маршрута |
| только `src` | `mangle_input` | нет |

Обратный трафик метить не нужно: он приходит по туннелю и возвращается по уже
готовым маршрутам. Трафик самого роутера через правило в prerouting не
проходит - роутер продолжает ходить в интернет напрямую.

### 3. Запуск и проверка

```sh
/usr/bin/qwdtt -s work start
/usr/bin/qwdtt status
```

```sh
ip rule show
ip route show table 51821
logread -e qwdtt-work
```

В `ip rule show` правило с приоритетом 9000 должно стоять выше правила 10000.
С компьютера `192.168.1.50` внешний адрес должен быть адресом второго сервера,
с любого другого - адресом первого.

## Цена

Каждый туннель держит свои сессии: при `workers` по умолчанию два туннеля - это
18 параллельных соединений. На слабом роутере это заметно, и `workers` у
второго туннеля имеет смысл уменьшить.
